How to Use This Document

This is both the Software Design Document (the architecture and the rules everything must obey) and the build plan (the ordered, checkable task list to realize it). It is written for an intermediate engineer to pick up and execute. The GDD (v6.2.4) remains the source of truth for what the game is; this document is how to build it and in what order.

  • Check boxes to track progress. Every task, asset, and test is a checkbox. State is saved in this browser (localStorage) — close and reopen and your progress is still here. The bar at the top is overall completion; each milestone shows its own count. "Reset" clears everything (with confirm).
  • Work milestones in order (M0 → M12). They form a vertical slice first sequence: by the end of M4 you have one playable battle end-to-end; everything after deepens and widens it. Each milestone lists what it depends on, so nothing is started before its foundation exists.
  • Each milestone has four groups: Tasks (the code), Assets needed (art/audio required by this milestone — use placeholders until M11), Tests (what to verify before moving on), and an Exit Criteria "definition of done."
  • AI prompts. Purple blocks are written to paste directly into the Claude model inside the Windsurf plugin (Cascade chat) in your JetBrains/IntelliJ IDE. They assume the file/architecture context of the surrounding tasks. Hit "copy", paste, and refine. They are starting points, not magic — always review generated Swift against the GDD and the determinism rules.
  • Definition of Done (global): a task is done when it (a) compiles, (b) has the tests listed for its milestone passing, (c) obeys the determinism contract, and (d) is committed with a message referencing the milestone (e.g. M4: deterministic tick loop).
Reality check on tooling

iOS + SpriteKit games are built and run through Xcode (toolchain, simulators, signing, asset catalogs, Game Center entitlements). The Windsurf/Claude plugin is used here for authoring and refactoring Swift — author in Windsurf, build/run/profile in Xcode. The two coexist on the same SwiftPM/Xcode project on disk. Where a task is Xcode-specific (entitlements, capabilities, asset catalog), it is noted.

Architecture — The One Rule Everything Obeys

The GDD's central promise is determinism: every battle is identical for every player on every run, which is what makes the puzzle learnable, the leaderboards fair, and replays shareable. That single promise dictates the entire architecture.

Simulation core ⟂ render layer (hard separation)

Split the codebase into two modules with a one-way dependency:

  • RivenkeepCore — a pure-Swift module with no import of SpriteKit/UIKit. It owns the grid, all units, all rules, the fixed-step tick loop, and the seeded RNG. It is fully unit-testable headless, runs identically on any device, and is the only place game state changes. It exposes a deterministic step(intents:) -> [Event] API.
  • RivenkeepRender — SpriteKit. It observes core state and the event stream and draws nodes/animations. It captures touch input and translates it into intents handed to the core. It never mutates game state directly. Animations interpolate between discrete tick states for smooth visuals (the standard GameplayKit-grid technique).
The determinism contract (every Core task must honor this)
  • Fixed logic tick = 0.5 s. The sim advances in discrete ticks, decoupled from frame rate. Render interpolates; logic never runs on deltaTime.
  • Seeded RNG only. All randomness flows through one GKMersenneTwisterRandomSource seeded from battleID. Never call Int.random, arc4random, Date(), or UUID() inside the sim.
  • Deterministic ordering. Iterate units in a stable order (sorted by spawn index, never a Set). Resolve simultaneous events by fixed tie-break rules.
  • Avoid float drift. Prefer integer grid coordinates and integer HP/damage. Where sub-grid position is needed (ship/projectile movement), use a fixed formula evaluation order and the same rounding everywhere.
  • Replay = seed + battle params + input timeline. Record the player's intents with their tick numbers; replaying them on the same seed must reproduce the exact end state. This is also the strongest determinism test (see M4).

Pattern reference: Apple's DemoBots shows SpriteKit + GameplayKit entities/components/state-machines at scale; this design keeps the simulation out of SpriteKit entirely for testability and determinism, which DemoBots does not, but borrows its component and state-machine structure on the render side.

The AI Layer — Apple Foundation Models

Rivenkeep treats Apple Intelligence (the on-device model behind Siri, exposed to apps via the Foundation Models framework, iOS 26+) as a first-class third layer alongside Core and Render — not an optional extra. It powers intelligent piece naming, the post-battle debrief, the living tutorial, rules help, dynamic flavor, accessibility narration, and recaps (full design in GDD → AI-Enhanced Experience). The model runs entirely on-device (private, free, offline).

The firewall is an architectural boundary, not a guideline

RivenkeepCore must not import the AI module (add the same build check that bans SpriteKit in Core). AI lives in a separate RivenkeepAI module that depends on Core's read-only summary types, never the reverse. AI consumes a structured post-hoc summary or player-facing text, runs off the timed loop (results screen, menus, naming UI — never a combat tick), and is non-authoritative: its output never flows back into game state, scoring, ranking, or the replay system. The determinism contract is preserved because the AI can only read finished outcomes and write cosmetic text.

Module shape

  • RivenkeepAI module. Depends on Core's BattleSummary, BoardSnapshot, and progression read-models. Exposes feature services: NameModerator, NameSuggester, DebriefCoach, TutorGuide, RulesAssistant, FlavorWriter, BoardNarrator, RecapWriter.
  • LanguageProvider protocol. All services talk to the model through one protocol (request → typed result). The default impl wraps SystemLanguageModel via LanguageModelSession. This makes the model swappable — Apple is opening the framework to Private Cloud Compute and to Claude/Gemini Swift packages — and lets tests inject a deterministic stub provider.
  • Guided generation everywhere. Use @Generable typed structs (e.g. Debrief, [PieceNameSuggestion], ModerationVerdict) so the app never parses free text. Use the Tool protocol for rules-grounded answers (the assistant calls into a rules lookup rather than inventing mechanics).

Availability & the required baseline (this is not "optional AI")

The AI path is the intended experience. Because Foundation Models requires an Apple-Intelligence-capable device with the feature on, each service ships with a baseline that guarantees coverage — framed as defense-in-depth, not a downgrade:

ServiceAI path (intended)Baseline (always present)
Name moderationOn-device classification + entity extractionRequired, fail-closed: denylist + pattern filter + community report. Safety can never depend solely on a gated feature.
Debrief / tutor / flavor / recapPersonalized generated textTemplated text built from the same structured summary (deterministic sentences keyed off the data).
Rules assistantNL answer grounded via tool-callingSearchable static FAQ / codex.

Build the baseline first (it's also the test fixture and the unsupported-device path), then layer the model on top. As Apple-Intelligence device penetration grows, the AI path becomes the universal experience without code changes.

Cross-cutting rules for every AI call

  • Async + cached. Never block a score, transition, or input. Cache results (re-opening a result is instant).
  • Moderate generated content too. Name suggestions and any UGC-adjacent output pass the same moderation as player input. No generated text references real people.
  • Privacy. On-device only; no player text or battle data leaves the device for AI. Matches the Production privacy posture.
  • Testability. Inject a stub LanguageProvider in tests; assert services degrade to baseline when the model is "unavailable," and that no AI type is reachable from RivenkeepCore.

Rule of thumb: if a piece of logic decides a game outcome, it lives in RivenkeepCore and has a unit test. If it only draws or animates, it lives in the app target. This boundary is what makes the determinism and balance claims verifiable.

Build Order — Why This Sequence

The order is vertical-slice-first: prove the riskiest, most novel thing (a deterministic Build puzzle that feels good, then a deterministic combat sim) before widening into content. By the end of M4 you can play one full battle (build → deploy → fight → win/lose) with one cannon and one ship. M5–M7 add the cast and the full loop; M8–M10 add progression, economy, and live services; M11 produces content; M12 polishes and ships. Each milestone is independently testable and leaves the game in a runnable state.

Implement the fixed-tick combat loop in RivenkeepCore (GDD "Fight Phase" + "Ship AI").
1 tick = 0.5s. Battle.step(intents:) advances exactly one tick and must be fully

Testing Strategy (Cross-Cutting)

Testing is embedded in every milestone above, but here is the overall strategy and the layers, so nothing is treated as an afterthought. The Core/Render split exists precisely so the game-deciding logic is testable headlessly.

DeterminismRecord→replay equality (same seed+inputs → identical end state), across simulated devices; ship/troop AI reproducibility; ranking integrity.XCTest harness from M4; run nightly + pre-release on a device matrix.
IntegrationPhase transitions, full sortie loop, save/sync/migration, IAP sandbox, analytics events, Remote Config override.XCTest + manual sandbox; per milestone + pre-release.

The one test that protects the whole design

The record→replay determinism test (M4) is the keystone. It guarantees the GDD's core promise (fair, learnable, rankable battles), it is the foundation of the replay-sharing feature, and it gives the server a way to re-simulate any submitted score from seed + inputs to catch cheating. Keep it green at all costs — any nondeterminism is a P0 regression.

Three checkpoints to stop and reassess
  • After M1: does the Build puzzle feel good in the hand? If not, fix it before building anything on top — it's the heart.
  • After M4: is the combat sim provably deterministic and is the auto-firing Fight engaging without manual aim? This is where the balance audit's biggest risk (early-game passivity vs Rampart's lead-the-target skill) gets decided. Prototype a combat skill verb here if it feels flat.
