▼ Part A — System Prerequisites
Base tooling on the Mac. Do these once. Xcode is required for iOS; Android Studio supplies the Android SDK + emulator.
A1Confirm macOS + Apple Silicon/Intel once

Flutter runs on macOS Sierra (10.14) or later. Confirm your version and chip.

sw_vers && uname -m

arm64 = Apple Silicon (M-series), x86_64 = Intel. Both are fine; just download matching installers where a choice is offered.

A2Install Homebrew once

Homebrew is the macOS package manager — the cleanest way to install Flutter and its helpers. Skip if brew --version already works.

/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
Note After install, follow the on-screen "Next steps" to add brew to your PATH (Apple Silicon puts it in /opt/homebrew/bin). Then run brew --version to confirm.
A3Install Xcode + Command Line Tools iOS

Install Xcode from the Mac App Store (large download, be patient). Then install the command-line tools and accept the license:

sudo xcodebuild -runFirstLaunch sudo xcodebuild -license accept xcode-select --install

Install an iOS Simulator runtime: open Xcode → Settings → Components → download an iOS simulator. Then verify:

open -a Simulator
Note You already use Xcode for iOS builds, so this is likely done — just confirm the license is accepted and a simulator runtime is present.
A4Install CocoaPods iOS

CocoaPods manages native iOS dependencies that Flutter plugins pull in (Firebase, ads, etc.).

brew install cocoapods
A5Install Android Studio (for the Android SDK + emulator) Android

Even though you'll code in IntelliJ, the simplest way to get the Android SDK, platform tools, and an emulator is to install Android Studio once and let it manage them.

brew install --cask android-studio

Launch it, run the setup wizard (installs SDK + platform-tools), then Tools → Device Manager → Create Device to make an emulator (e.g., Pixel 8, latest API).

A6Install the Flutter SDK once

The Dart SDK is bundled inside Flutter — you do not install Dart separately.

brew install --cask flutter

Confirm it's on your PATH and note the install path (you'll need it in IntelliJ):

which flutter && flutter --version
SDK path Homebrew installs Flutter at /opt/homebrew/share/flutter (Apple Silicon) or /usr/local/share/flutter (Intel). Run dirname $(dirname $(which flutter)) to print the exact top-level folder — copy it for step B3.
A7Run flutter doctor and resolve issues

This is your health check. It downloads Flutter's own dependencies on first run, then reports what's missing.

flutter doctor -v

Work through anything flagged in bold. Two common ones:

A8Accept Android SDK licenses Android
flutter doctor --android-licenses

Press y through each license. Re-run flutter doctor — the Android toolchain line should turn green.

▼ Part B — Dart & Flutter in IntelliJ IDEA
The part you asked for. Installing the Flutter plugin auto-installs the Dart plugin — you don't add Dart separately.
B1Install / update IntelliJ IDEA once

Either edition works for Flutter — Community (free) is fully supported. Ultimate adds web/enterprise tooling you won't need for the game. Update to a current version (2024.x or later).

brew install --cask intellij-idea-ce

(Or intellij-idea for Ultimate if you already license it.)

B2Install the Flutter plugin (Dart comes with it)

Launch IntelliJ. From the Welcome screen (or ⌘, in an open project) open Settings → Plugins. Select Marketplace, search Flutter, click Install.

When prompted, click Yes / Install to also add the Dart plugin — it's required and pulled in automatically. Click Restart when done.

Why The Flutter plugin powers run/debug/hot-reload; the Dart plugin powers code analysis, completion, and formatting. You need both, and installing Flutter guarantees both.
B3Point IntelliJ at the Flutter SDK

Open Settings → Languages & Frameworks → Flutter. In Flutter SDK path, paste the top-level Flutter folder from step A6 (e.g., /opt/homebrew/share/flutter). Apply.

The Dart SDK path auto-fills to the bundled copy inside Flutter (.../flutter/bin/cache/dart-sdk) — you should not have to set it manually. Confirm it's populated under Languages & Frameworks → Dart.

B4Turn on format-on-save + analysis (recommended)

In Settings → Languages & Frameworks → Dart, enable "Format code on save" and "Organize imports on save". This keeps the codebase clean with zero effort — matches your zero-tolerance-for-mess standard.

The Dart Analysis panel (bottom toolbar) shows lints/errors live as you type, like IntelliJ's Java inspector.

▼ Part C — Create & Run the Project
Scaffold the app, wire up a device on each platform, and confirm hot reload before writing any game code.
C1Create the Flutter project

In IntelliJ: File → New → Project → Flutter (from the Generators list). Set the Flutter SDK path, then:

— Name: rivenkeep
— Project location: your dev folder
— Org / company domain: reverse-DNS you control (e.g., studios.riquochet) — this becomes the bundle/app ID
— Platforms: check iOS and Android (and Web later if you want a test target)

Prefer the terminal? Equivalent:

flutter create --org studios.riquochet --platforms=ios,android rivenkeep
C2Run on the iOS Simulator iOS

Open the Simulator (open -a Simulator), select it in IntelliJ's device dropdown (top-right), and click the green Run arrow — or:

flutter run -d ios

You should see the Flutter starter counter app boot in the simulator.

C3Run on the Android Emulator Android

Start the emulator you created in A5 (Device Manager), select it in the device dropdown, Run — or:

flutter emulators --launch <emulator_id> flutter run -d android

List available emulator IDs with flutter emulators.

C4Confirm Hot Reload

With the app running, edit the starter text in lib/main.dart and save. IntelliJ hot-reloads in under a second (or press the ⚡ Hot Reload button). Seeing the change instantly = your loop is healthy.

This is the payoff Hot reload is why this stack beats the Xcode/Swift build cycle for iteration. Confirm it works now.
▼ Part D — Rivenkeep Dependencies & Structure
Add the engine, backend, and services from the GDD's architecture, and lay out the logic-vs-render folder split.
D1Add core dependencies

From the project root, add the engine and service packages the GDD specifies. Run these flutter pub add commands (they write to pubspec.yaml and fetch):

flutter pub add flame flutter pub add firebase_core cloud_firestore firebase_auth cloud_functions firebase_remote_config firebase_analytics flutter pub add games_services flutter pub add in_app_purchase flutter pub add google_mobile_ads flutter pub add video_player

Then fetch everything:

flutter pub get
D2Set up the Firebase project (FlutterFire)

Install the Firebase CLI + FlutterFire CLI, log in, and configure both platform apps under one Firebase project named rivenkeep-prod:

brew install firebase-cli dart pub global activate flutterfire_cli firebase login flutterfire configure --project=rivenkeep-prod

This registers the iOS and Android apps, downloads their config, and generates lib/firebase_options.dart. Initialize Firebase in main() before runApp().

Order Create the Firebase project in the console first (or let the CLI create it). You'll need a Google account; the free Spark tier covers development.
D3Create the logic-vs-render folder structure

The GDD mandates a pure-Dart Core layer with zero rendering/platform dependencies, kept separate from the render layer. Scaffold it:

mkdir -p lib/core lib/render lib/services lib/models # lib/core/ → pure logic: grid, piece state machine, enclosure flood-fill, # tick combat, A* pathfinding, star calc. NO Flutter imports. # lib/render/ → Flame game + Flutter widgets that draw Core state # lib/services/→ SyncService, LeaderboardService, StoreService, etc. # lib/models/ → shared immutable data classes
Discipline Nothing in lib/core/ may import 'package:flutter/...' or any plugin. That's what keeps the simulation deterministic and unit-testable — the same principle as your pure-logic Core layer plan.
D4Initialize Git

flutter create adds a .gitignore already. Initialize and make the first commit:

git init && git add -A && git commit -m "Initial Flutter scaffold + Rivenkeep deps"
D5Verify the full stack builds on both platforms

With Firebase + plugins added, native pods/gradle change. Do a clean build on each target to catch config issues early:

flutter clean && flutter pub get flutter run -d ios flutter run -d android

Both should launch the app with Firebase initialized and no plugin errors in the console.

▼ Part F — Asset Creation Pipeline (AI Art)
The art-production workflow you'll stand up at the art milestone (M11 in the SDD — placeholder shapes carry you until then, so this is not blocking early engineering). Rivenkeep is a realistic style, not pixel art, so the tools below are the realistic/HD track — ignore pixel-specific tools (PixelLab, Sprixen, Retro Diffusion). Everything here outputs transparent PNG sprite sheets / texture atlases, which are engine-neutral (identical whether the renderer is Flame or anything else).
The #1 rule Rivenkeep needs 800+ sprites that all look like one game. Style consistency — not any single sprite's quality — is what makes or breaks AI-generated game art. The entire pipeline below is built around locking one house style first (F1) and generating everything else from it. Do F1 before any production art.
F1Write the art bible + train a house-style model keystone

Define the look in a short art bible: realistic materials, the ~30° isometric tilt for the 2.5D battlefield (Age of Empires is the GDD's reference), the flatter clean readability for the 2D Build/Deploy map, palette, lighting direction, and the team-color outline treatment.

Then lock it with a custom-trained model so every later asset shares visual DNA:

— Scenario (scenario.com) is the strongest option for this: upload 20–30 reference images of your target style and train a private model. Every generation then comes out on-brand. Custom training is on the ~$45/mo tier; image plans start ~$15/mo.

— Alternatives if you don't want to train: Layer.ai (character-consistency engine, strong multi-pose sprite consistency) or Ludo.ai (all-in-one asset stack, API + MCP, connects to Claude). These use reference images rather than a trained model, so consistency is good but not as locked as Scenario.

Do this once The trained model IS your art direction. Everything in F2–F5 is generated from it. Re-train only if you deliberately change the game's look.
F2Generate 2D top-down assets (Build/Deploy Map View)

Flat overhead sprites for the puzzle view: wall blocks (clean / cracked <75% / spackle states), enclosure floor tiles (dark + mirrored gray), and top-down castle states. Generate from your F1 model with an overhead-orthographic framing prompt.

Output: transparent PNG sized to 1× grid cell (crack states as overlays, per the SDD asset table). Keep the base wall neutral so the runtime team-color outline shader reads cleanly on top.

F3Generate seamless terrain + theater map tiles

Ten theaters, each needing tileable ground plus its water/lava/void surface. Generate seamless / tileable textures (Scenario and most SDXL/Flux workflows have a tiling toggle) so they repeat without visible seams across the board.

Clarify — maps ≠ 190 hand-drawn images The 190 battle overlays are data (JSON rock/tree/cliff placement per battle, per the SDD), not individual artworks. You produce the reusable tile set per theater; the overlays are authored/generated placement data that arranges those tiles. This is why "190 battlefields" is a data task, not 190 art commissions.

F4Generate 2.5D isometric assets via 3D → render

The GDD specifies the Fight view as "pre-rendered 2D assets from 3D models" — this is the right call because it gives consistent, controllable multi-angle sprites. The workflow:

a. Image-to-3D from your F1 concept art (so the style carries into 3D): Meshy (meshy.ai) is the best all-round pipeline — image/text-to-3D + PBR textures + auto-rig + GLB/FBX export, browser-based. Rodin / Hyper3D for higher topology quality; Luma Genie (free) or Tripo for fast prototyping.

b. Import the GLB into Blender (free) and set an orthographic camera at the GDD's isometric angle (~30° tilt).

brew install --cask blender

c. Render each needed state/angle to transparent PNG: cannons need a barrel-rotation set + enclosed/exposed + HP tint; ships need per-type profiles (and later 10 theater skins); castles need enclosed/not-enclosed + 3 degradation states; bosses need stealth/surface + attack-tell frames.

d. One consistent camera + light rig rendering every model = a coherent isometric set, because they're all lit and angled identically. This is the big advantage over generating isometric sprites directly.

F5Produce animation frames (troops + VFX)

Troops need short walk cycles (2–4 frames) and the Shield Bearer needs facing variants. Auto-rig the 3D troop model in Meshy and render animation frames from the same Blender rig as F4, or use Layer.ai for multi-pose consistency. Expect manual touch-up — AI animation is still the weakest category in 2026.

For VFX (projectiles, explosions, lightning arcs, freeze, lava, screen shake, the isolation-wipe), prefer the engine's particle system over pre-baked sprite sheets where you can — it's smaller, scalable, and tint-able at runtime.

F6Clean up + enforce SDD conventions

Raw AI/render output is almost never a drop-in asset. Clean up with Pixelorama (free, open-source) or your editor of choice: crisp background removal for clean transparency, palette enforcement, grid alignment.

brew install --cask pixelorama

Apply the SDD's asset conventions as you export: naming <group>_<name>_<state>@<scale>x (e.g. cannon_lightning_exposed@2x), and set each sprite's anchor — plus a muzzle point for cannons and a hull-center for ships — since the sim→render mapping relies on them.

F7Pack atlases + wire into the game

Pack finished sprites into per-theater texture atlases (theater_<name>.atlas per the SDD), a shared UI atlas, and a shared units atlas until theater skins exist. Use TexturePacker or the engine's built-in sprite-sheet tooling, then load through the game's asset loader.

Milestone fit Per the SDD, real art lands at M11 — you build the whole game on placeholder shapes first, then drop in these atlases near the end. That means you can defer this entire Part until the game plays well; don't let art block engineering.
